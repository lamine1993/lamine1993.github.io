ArSaTool: a React Native app to diagnose crop pests

Faced with a damaged plant, a farmer wants to know two things: which insect is to blame, and how to fight it. ArSaTool answers both questions from the phone.

By Mohamadou Lamine SarrOctober 22, 20267 min read

I built ArSaTool in 2019-2020. The app guides the user through three choices: the affected part of the plant (leaves, for example), the crop, then the attack. It then shows a technical sheet with the insect, the damage and the control method. If the user cannot find a match, they can photograph the plant and send the picture.

The stack

  • React Native for an Android and iOS app from a single JavaScript codebase.
  • Redux and Redux Thunk for global state and asynchronous calls.
  • React Navigation (drawer, stacks and an auth loading screen).
  • Native Base for UI components.
  • react-native-camera and react-native-fetch-blob for taking and uploading photos.

State split by domain

The Redux store is split into three parts, each with its own reducer:

const rootReducer = combineReducers({
  recherche: rechercheReducer,  // crops, attacks, current selection
  connexion: connexionReducer,  // user and token
  ui: uiReducer                 // loading, errors, success
});

Separating UI state (ui) from the rest is the choice that simplified the code the most. Every async action follows the same pattern: uiStartLoading, the call, then uiStopLoading or uiShowError with a clear message. Every screen shows loading and errors the same way.

Loading sheets and their images in parallel

An attack sheet needs two sets of images: the damage and the insect. Loading them one by one would have been slow on a mobile network. With Promise.all, all requests go out at once:

fetch(SERVER + 'listattaquecomplet/' + culture.id + '/' + localisation)
  .then(res => res.json())
  .then(attaques => Promise.all([
    Promise.all(attaques.map(a =>
      fetch(SERVER + 'imageAttaques/' + a.id).then(r => r.json()))),
    Promise.all(attaques.map(a =>
      fetch(SERVER + 'imageInsectes/' + a.insecte.id).then(r => r.json())))
  ]).then(([imagesAttaques, imagesInsectes]) => {
    // each attack gets its images, then a single Redux action
    dispatch(setAttaques(merge(attaques, imagesAttaques, imagesInsectes)));
  }));

The wait becomes the time of the slowest request rather than the sum of all of them. The screen updates once, with complete data.

Uploading a photo to the server

The photo screen uses RNCamera, with flash, zoom, focus and white balance controls. Once the photo is taken, it is sent as multipart/form-data, along with the farmer's details:

RNFetchBlob.fetch('POST', SERVER + 'imageEnvoye',
  { 'Content-Type': 'multipart/form-data' },
  [
    { name: 'file', filename: 'photo.jpg', data: RNFetchBlob.wrap(path) },
    { name: 'agriculteur', data: JSON.stringify({ agriculteurId, flag: true }) }
  ]);

RNFetchBlob.wrap sends the file straight from its path on the phone, without loading it fully into memory as base64. That matters on entry-level phones.

Rich content, validated on the server

The sheets come from an agronomic knowledge base: damage description, damage type (deformation, for example), validation date. The flag field and the validation date show that content, like uploaded photos, goes through validation before it is published.

What I would do differently today

  • An offline cache for sheets: farming areas often have little network coverage.
  • Photo compression before upload, and resumable uploads after a drop.
  • Redux Toolkit or React Query to cut repetitive API code.
  • TypeScript to secure the crop, attack and insect model.

What this project taught me

ArSaTool taught me to structure an app around its data: a catalog, relationships (crop, attack, insect, images) and a validation process. That is exactly what I find in the CMDB today: objects, their relationships, and rules that guarantee the quality of the information.
