Decommissioning servers with ServiceNow: method and teamwork with infrastructure

Shutting down a server takes a minute. Being sure nobody depends on it takes much longer. Here is how I structure that work as Tech Lead of a server decommissioning squad.

By Mohamadou Lamine SarrOctober 22, 20267 min read

In large organizations, servers pile up: old applications, forgotten test environments, machines whose owner has moved to another team. Each one costs money in licenses, power and maintenance, and adds security exposure.

Retiring them is a real lever. But a poorly prepared retirement can cut off a service nobody had linked to that server. My role as Tech Lead at Desjardins is to make this work safe, traceable and repeatable, in constant contact with the infrastructure teams.

Why ServiceNow sits at the center of the process

Decommissioning involves many teams: servers, storage, network, backup, security, application owners. ServiceNow is the shared source of truth:

  • the CMDB says what exists and what depends on it;
  • Change Management governs every retirement and keeps a record of approvals;
  • the CI lifecycle (CSDM) says where each server stands;
  • Asset Management takes over for hardware and license end of life.

6 steps to a retirement with no incident

1. Identify candidates

We start from concrete signals: a CI Discovery has not seen for a long time, a server with no related application, an application at end of life, an operating system out of support. The list is then validated with the infrastructure teams, who often know the history better than the CMDB does.

2. Analyze dependencies

This is the most important step. Before any retirement, I check the CI's relationships in both directions: what runs on the server and what depends on it. The relationship view and the dependency map help a lot. To process a batch, a simple query on the relationship table is enough:

// List a server's relationships, in both directions
var rel = new GlideRecord('cmdb_rel_ci');
var q = rel.addQuery('parent', serverSysId);
q.addOrCondition('child', serverSysId);
rel.query();
while (rel.next()) {
  gs.info(rel.parent.getDisplayValue() + ' → ' +
          rel.type.getDisplayValue() + ' → ' +
          rel.child.getDisplayValue());
}

No CMDB is ever 100% complete. That is why the analysis does not stop at ServiceNow: it is confirmed with application owners and the infrastructure teams.

3. Get approvals

Every retirement goes through a change request. It lists the affected CIs, the identified impacts, the rollback plan and the owners' approvals. If an incident happens later, we know exactly what was retired, when, and who agreed to it.

4. Observe before deleting

Instead of deleting right away, we first isolate or power off the server for an observation period. If a service complains, we power it back on in minutes. If nothing happens during that period, we move on. It is the best insurance against dependencies nobody had documented.

5. Retire for good

The technical retirement follows a fixed checklist shared with infrastructure: final backup if needed, removal from monitoring, DNS and IP address cleanup, storage release, license termination, then secure wipe or disposal of the hardware.

6. Update the CMDB

A server that is gone but still "Operational" in the CMDB skews reports, impact analysis and audits. So we move the CI to the End of Life lifecycle stage with the Retired status, and remove it from Discovery schedules so it does not come back.

Watch out

Do not delete the CI: retire it. Its history, past relationships and related changes remain useful for audits. Deletion or archiving comes later, under clear policies, for example in CMDB Data Manager.

Working with infrastructure teams

Most of my work is talking with the infrastructure teams. Decommissioning succeeds when the ServiceNow team and infrastructure move forward together. What works, in my experience:

  • Speak their language. For infrastructure, a server is a name, an IP, a cluster. For the CMDB, it is a CI with a class and relationships. My role is to bridge the two.
  • A regular check-in. Short, with the list of servers in progress and the blockers. Decisions are recorded in the change, not only in a chat.
  • Automate what repeats. Any manual task repeated between ServiceNow and infrastructure is a candidate for a flow: task creation, owner reminders, CI update when the change closes.
  • Report the gaps. Every time infrastructure finds a dependency missing from the CMDB, it is data to fix. Decommissioning improves the CMDB along the way.

Key takeaways

  • The hard part of decommissioning is not technical: it is proving a server is no longer used.
  • A reliable CMDB makes every retirement faster, and every well-run retirement makes the CMDB more reliable.
  • The relationship with infrastructure matters as much as the tools. Without it, the best CMDB in the world is not enough.
