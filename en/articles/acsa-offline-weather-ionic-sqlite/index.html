ACSA: an offline weather app with audio bulletins, built with Ionic and SQLite

A forecast is only useful if it reaches its audience. ACSA is a weather app prototype designed around two constraints: a network that often drops, and users who would rather listen than read.

By Mohamadou Lamine SarrOctober 22, 20266 min read

I built ACSA as a prototype in late 2019 and early 2020. It shows the day's forecast for a zone in Senegal and offers an audio bulletin that summarizes the weather. The main technical challenge: keep the information available even without a connection.

The stack

  • Ionic 3 and Angular, in TypeScript, with lazy-loaded pages.
  • SQLite through Cordova to store bulletins on the phone.
  • Ionic Audio to play audio bulletins in the app.
  • Moment.js to handle bulletin dates.

A data model that follows the territory

A forecast is tied to a precise geographic breakdown: zone, region and department. The model mirrors it:

export interface MeteoZone {
  zone: string;          // NORD, CENTRE OUEST, CENTRE, SUD
  region: string;        // SAINT-LOUIS, DAKAR, THIES, MATAM…
  departement: string;
  paysage_ciel: string;  // sky conditions
  temperature?: number;
  temperatureMax?: number;
  temperatureMin?: number;
  humidite?: number;
  vent?: string;
}

export interface BulletinMeteo {
  prevision?: MeteoZone;
  resume?: AudioType;       // the audio bulletin
  intervalleDate?: DateMeteo;
}

A bulletin brings together three things: the forecast figures, the audio file and the period covered.

Local storage first

The app always reads its data from SQLite, never straight from the network. Each bulletin is stored with its zone and the date it was added, so the day's forecast comes back in a single query:

getMeteo(zone: string, today: string) {
  return this._db.query(
    'SELECT prevision, audio, dateAjout FROM meteo ' +
    'WHERE zone = ? AND dateAjout = ? LIMIT 1',
    [zone, today]);
}

Complex objects (forecast, audio, period) are stored as JSON in text columns. It is a deliberate trade-off for a prototype: the schema stays simple and the model can change without migrations.

Why read locally?

If the screen always reads the local database, it behaves the same with or without a network. Synchronization becomes a separate concern that updates the database whenever a connection exists.

Decoupled components

The weather page combines two components: bulletin-audio, which shows the player, and donnee-meteo, which shows temperature, wind and sky. The page passes them the bulletin and EventEmitters that signal when it opens and closes. The player can then stop cleanly when the user leaves the screen.

Where the prototype stood

The prototype runs on sample bulletins loaded at startup, for one zone. It validates the interface, the data model and offline reading. The planned next step was synchronization with a bulletin server.

What I would do differently today

  • Real synchronization: download the week's bulletins whenever a connection exists, then clean up old ones.
  • Zone selection by the user, or detection through GPS.
  • Audio bulletins in local languages, and an "audio first" mode for users who read little.
  • A more structured SQL schema once the model is stable.

What this project taught me

ACSA taught me to start from users' real constraints rather than from the technology: an unstable network, a preference for spoken information. It is the same approach as for an employee portal: start from how people look for information, not from how the organization is structured.
