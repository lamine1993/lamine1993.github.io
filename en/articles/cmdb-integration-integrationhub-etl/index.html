Integrating Zabbix and Workspace ONE with the ServiceNow CMDB using IntegrationHub ETL

Two sources, two ways of describing a device, one rule: never create a duplicate CI. Here is the method I used to connect a network monitoring tool and an MDM to the CMDB.

By Mohamadou Lamine SarrOctober 22, 20268 min read

On a project at PSG, I integrated two platforms with the ServiceNow CMDB: Zabbix, which monitors the network estate, and Workspace ONE, which manages mobile devices. The need is a common one: the CMDB must reflect what really exists, with no manual data entry.

The trap is just as common. A poorly designed import creates duplicates, overwrites more reliable data, and the CMDB loses the teams' trust. This article covers the architecture we chose and the decisions that matter.

The architecture at a glance

Each source follows the same path:

  1. MID Server: the bridge between the ServiceNow instance and the internal network where Zabbix lives.
  2. Data source: calls the tool's API and loads the raw data into an import set table.
  3. IntegrationHub ETL: transforms the data and maps it to the right CMDB classes, using the Robust Transform Engine.
  4. IRE (Identification and Reconciliation Engine): decides whether each row matches an existing CI or a new one, and which source may update which field.

The last step is the key one. With a classic Transform Map, the script writes to the CMDB. With IntegrationHub ETL, everything goes through the IRE. That is what protects the CMDB from duplicates.

Step 1: secure the connection with the MID Server

Zabbix was hosted on the internal network, with no direct access from the Internet. The MID Server is the right answer: installed inside that network, it opens an outbound connection to the instance and runs the calls on its behalf.

A few rules I always apply:

  • A dedicated service account with read-only rights on the source tool's API.
  • Credentials stored in a ServiceNow Credential record, never in plain text in a script.
  • A MID Server validation and an API call test before building anything in the ETL.

Step 2: pull data from the source

Zabbix exposes a JSON-RPC API. The host.get method returns hosts with their interfaces and inventory. I deliberately limit the requested fields: import what the CMDB will use, nothing more.

{
  "jsonrpc": "2.0",
  "method": "host.get",
  "params": {
    "output": ["hostid", "host", "name", "status"],
    "selectInterfaces": ["ip", "dns", "type"],
    "selectInventory": ["os", "serialno_a", "vendor", "model"]
  },
  "id": 1
}

For Workspace ONE, the UEM REST API lets you search devices with their serial number, model, platform and assigned user. In both cases I built custom data sources that handle pagination and load each response into an import set table.

Tip

Keep the data source "dumb": it fetches and it loads, nothing else. All transformation logic belongs in the ETL, where it is visible, testable and documented.

Step 3: transform with IntegrationHub ETL

IntegrationHub ETL is a guided application. For each source, I followed its steps:

Prepare the data

Clean before mapping: lowercase host names, split out the domain name, normalize manufacturer names ("Cisco Systems" and "cisco" must become the same value), and set aside rows without a reliable identifier.

Map to CMDB classes

Each row must land in the right class: a switch in cmdb_ci_ip_switch, a router in cmdb_ci_ip_router, a smartphone in the mobile device class. A classification rule based on the type reported by the source avoids dumping everything into a generic class.

Add relationships

An isolated CI has little value. When the source allows it, I create relationships during the import: the network interface linked to its device, the mobile device linked to its user.

Test, then roll back

The ETL lets you run a test import on a sample, then undo it (rollback). I always run several passes like this before the first real import. It is the most underrated feature of the tool.

Step 4: configure the IRE properly

This is where CMDB quality is won or lost. Three settings are essential.

SettingPurposeWhat I did
Discovery sourceRecord where each CI comes fromA dedicated value per tool, to trace and filter each source
Identification rulesRecognize an existing CISerial number first, then fully qualified host name as a fallback
Reconciliation rulesDecide which source writes which fieldDiscovery stays authoritative for technical attributes; Workspace ONE is authoritative for the device's user

Without reconciliation rules, the last source to run wins. Two tools can then keep overwriting each other on every import, and the CI history becomes unreadable.

Step 5: monitor quality over time

An integration is never finished on go-live day. I set up regular monitoring:

  • The CMDB Health dashboard, to track CI completeness, compliance and freshness.
  • The de-duplication tasks the IRE creates when it detects duplicates, reviewed and remediated one by one.
  • A review of rejected rows after each import, to fix the source rather than the CMDB.

Key takeaways

  • The IRE is not optional. Every import into the CMDB should go through it.
  • Identifiers first. Without a reliable serial number, no rule can save data quality.
  • Talk to the business teams. I ran a workshop with the network and mobility teams before building anything. That is where you learn which source is authoritative for each piece of data.

Going further, the same logic applies to Store connectors: Service Graph Connectors rely on the same building blocks (import, Robust Transform, IRE). Understanding the ETL means understanding how they work.
