Intégrer Zabbix et Workspace ONE à la CMDB ServiceNow avec IntegrationHub ETL

Deux sources, deux façons de décrire un équipement, une seule règle : ne jamais créer un CI en double. Voici la méthode que j'ai appliquée pour brancher un outil de supervision réseau et un MDM sur la CMDB.

Par Mohamadou Lamine Sarr22 octobre 2026Lecture : 8 min

Lors d'une mission chez PSG, j'ai eu à intégrer deux plateformes à la CMDB ServiceNow : Zabbix, qui supervise le parc réseau, et Workspace ONE, qui gère les appareils mobiles. Le besoin est classique : la CMDB doit refléter ce qui existe vraiment, sans saisie manuelle.

Le piège l'est aussi. Un import mal conçu crée des doublons, écrase des données plus fiables, et la CMDB perd la confiance des équipes. Cet article décrit l'architecture retenue et les décisions qui comptent.

L'architecture en un coup d'œil

Chaque source suit le même chemin :

  1. MID Server : il fait le lien entre l'instance ServiceNow et le réseau interne où vit Zabbix.
  2. Data source : elle appelle l'API de l'outil et charge les données brutes dans une table d'import.
  3. IntegrationHub ETL : il transforme ces données et les associe aux bonnes classes de la CMDB, grâce au Robust Transform Engine.
  4. IRE (Identification and Reconciliation Engine) : il décide si chaque ligne correspond à un CI existant ou à un nouveau CI, et quelle source a le droit de modifier quel champ.

Le point clé est le dernier. Avec un Transform Map classique, c'est le script qui écrit dans la CMDB. Avec IntegrationHub ETL, tout passe par l'IRE. C'est ce qui protège la CMDB des doublons.

Étape 1 : sécuriser la connexion avec le MID Server

Zabbix était hébergé dans le réseau interne, sans accès direct depuis Internet. Le MID Server est la bonne réponse : installé dans ce réseau, il ouvre une connexion sortante vers l'instance et exécute les appels pour elle.

Quelques règles que j'applique systématiquement :

  • Un compte de service dédié, avec des droits en lecture seule sur l'API de l'outil source.
  • Les identifiants stockés dans un Credential ServiceNow, jamais en clair dans un script.
  • Une vérification du MID (Validate) et un test de l'appel API avant de construire quoi que ce soit dans l'ETL.

Étape 2 : récupérer les données de la source

Zabbix expose une API JSON-RPC. La méthode host.get renvoie les hôtes avec leurs interfaces et leur inventaire. Je limite volontairement les champs demandés : on importe ce que la CMDB va utiliser, rien de plus.

{
  "jsonrpc": "2.0",
  "method": "host.get",
  "params": {
    "output": ["hostid", "host", "name", "status"],
    "selectInterfaces": ["ip", "dns", "type"],
    "selectInventory": ["os", "serialno_a", "vendor", "model"]
  },
  "id": 1
}

Pour Workspace ONE, l'API REST de l'UEM permet de rechercher les appareils, avec le numéro de série, le modèle, la plateforme et l'utilisateur associé. Dans les deux cas, j'ai construit des data sources personnalisées qui gèrent la pagination et chargent chaque réponse dans une table d'import.

Conseil

Garde la data source « bête » : elle récupère et elle charge, c'est tout. Toute la logique de transformation va dans l'ETL, où elle est visible, testable et documentée.

Étape 3 : transformer avec IntegrationHub ETL

IntegrationHub ETL est un assistant guidé. Pour chaque source, j'ai suivi ses étapes :

Préparer les données

Nettoyer avant de mapper : mettre les noms d'hôte en minuscules, séparer le nom de domaine, normaliser les noms de fabricants (« Cisco Systems » et « cisco » doivent devenir la même valeur), écarter les lignes sans identifiant fiable.

Associer aux classes CMDB

Chaque ligne doit aller dans la bonne classe : un commutateur dans cmdb_ci_ip_switch, un routeur dans cmdb_ci_ip_router, un smartphone dans la classe des appareils mobiles. Une règle de classification fondée sur le type remonté par la source évite de tout mettre dans une classe générique.

Ajouter les relations

Un CI isolé a peu de valeur. Quand la source le permet, je crée les relations dès l'import : l'interface réseau rattachée à son équipement, l'appareil mobile rattaché à son utilisateur.

Tester, puis annuler

L'ETL permet de lancer un import de test sur un échantillon, puis de l'annuler (rollback). Je fais toujours plusieurs passages ainsi avant le premier import réel. C'est la fonction la plus sous-estimée de l'outil.

Étape 4 : bien régler l'IRE

C'est ici que se joue la qualité de la CMDB. Trois réglages sont essentiels.

RéglageRôleCe que j'ai fait
Source de découverteIndiquer d'où vient chaque CIUne valeur dédiée par outil, pour tracer et filtrer chaque source
Règles d'identificationReconnaître un CI existantLe numéro de série d'abord, puis le nom d'hôte complet en second recours
Règles de réconciliationDécider quelle source écrit quel champDiscovery reste prioritaire sur les attributs techniques ; Workspace ONE fait foi pour l'utilisateur de l'appareil

Sans règles de réconciliation, la dernière source qui passe a raison. Deux outils peuvent alors se corriger l'un l'autre à chaque import, et l'historique du CI devient illisible.

Étape 5 : surveiller la qualité dans la durée

Une intégration n'est jamais terminée le jour de sa mise en production. J'ai mis en place un suivi régulier :

  • Le tableau de bord CMDB Health, pour suivre l'exhaustivité, la conformité et la fraîcheur des CI.
  • Les tâches de déduplication créées par l'IRE quand il détecte des doublons, traitées et remédiées une par une.
  • Une revue des lignes rejetées à chaque import, pour corriger la source plutôt que la CMDB.

Ce que je retiens

  • L'IRE n'est pas une option. Tout import vers la CMDB doit passer par lui.
  • Les identifiants avant tout. Sans numéro de série fiable, aucune règle ne peut sauver la qualité des données.
  • Parler avec les équipes métier. J'ai animé un atelier avec les équipes réseau et mobilité avant de construire quoi que ce soit. C'est là qu'on apprend quelle source fait foi pour chaque information.

Pour aller plus loin, la même logique s'applique aux connecteurs du Store : les Service Graph Connectors reposent sur les mêmes briques (import, Robust Transform, IRE). Comprendre l'ETL, c'est comprendre comment ils fonctionnent.
