ArSaTool : une application React Native pour diagnostiquer les ravageurs des cultures

Face à une plante abîmée, l'agriculteur veut savoir deux choses : quel insecte est en cause, et comment lutter contre lui. ArSaTool répond à ces deux questions depuis le téléphone.

Par Mohamadou Lamine Sarr22 octobre 2026Lecture : 7 min

J'ai développé ArSaTool en 2019-2020. L'application guide l'utilisateur en trois choix : la partie de la plante touchée (feuilles, par exemple), la culture, puis l'attaque. Elle affiche alors une fiche technique avec l'insecte, les dégâts et la méthode de lutte. Si l'utilisateur ne trouve pas, il peut photographier la plante et envoyer la photo.

La pile technique

  • React Native pour une application Android et iOS à partir d'un seul code JavaScript.
  • Redux et Redux Thunk pour l'état global et les appels asynchrones.
  • React Navigation (tiroir, piles et écran de chargement d'authentification).
  • Native Base pour les composants d'interface.
  • react-native-camera et react-native-fetch-blob pour la photo et son envoi.

Un état découpé par domaine

Le store Redux est découpé en trois parties, chacune avec son reducer :

const rootReducer = combineReducers({
  recherche: rechercheReducer,  // cultures, attaques, sélection en cours
  connexion: connexionReducer,  // utilisateur et jeton
  ui: uiReducer                 // chargement, erreurs, succès
});

Séparer l'état de l'interface (ui) du reste est le choix qui a le plus simplifié le code. Chaque action asynchrone suit le même schéma : uiStartLoading, l'appel, puis uiStopLoading ou uiShowError avec un message clair. Tous les écrans affichent le chargement et les erreurs de la même façon.

Charger les fiches et leurs images en parallèle

Une fiche d'attaque a besoin de deux séries d'images : celles des dégâts et celles de l'insecte. Les charger une par une aurait été lent sur un réseau mobile. Avec Promise.all, toutes les requêtes partent en même temps :

fetch(SERVER + 'listattaquecomplet/' + culture.id + '/' + localisation)
  .then(res => res.json())
  .then(attaques => Promise.all([
    Promise.all(attaques.map(a =>
      fetch(SERVER + 'imageAttaques/' + a.id).then(r => r.json()))),
    Promise.all(attaques.map(a =>
      fetch(SERVER + 'imageInsectes/' + a.insecte.id).then(r => r.json())))
  ]).then(([imagesAttaques, imagesInsectes]) => {
    // chaque attaque reçoit ses images, puis une seule action Redux
    dispatch(setAttaques(fusionner(attaques, imagesAttaques, imagesInsectes)));
  }));

Le temps d'attente devient celui de la requête la plus lente, et non la somme de toutes les requêtes. L'écran est mis à jour une seule fois, avec des données complètes.

Envoyer une photo au serveur

L'écran photo utilise RNCamera, avec le flash, le zoom, la mise au point et la balance des blancs. Une fois la photo prise, elle part en multipart/form-data, accompagnée des informations de l'agriculteur :

RNFetchBlob.fetch('POST', SERVER + 'imageEnvoye',
  { 'Content-Type': 'multipart/form-data' },
  [
    { name: 'file', filename: 'photo.jpg', data: RNFetchBlob.wrap(path) },
    { name: 'agriculteur', data: JSON.stringify({ agriculteurId, flag: true }) }
  ]);

RNFetchBlob.wrap envoie le fichier directement depuis son chemin sur le téléphone, sans le convertir entièrement en base64 en mémoire. C'est important pour les téléphones d'entrée de gamme.

Un contenu riche, validé côté serveur

Les fiches viennent d'une base de connaissances agronomique : description des dégâts, type de dégât (déformation, par exemple), date de validation. Le champ flag et la date de validation montrent que le contenu, comme les photos envoyées, passe par une validation avant d'être publié.

Ce que je ferais autrement aujourd'hui

  • Un cache hors ligne des fiches : les zones agricoles ont souvent peu de réseau.
  • La compression des photos avant l'envoi, et une reprise en cas de coupure.
  • Redux Toolkit ou React Query pour réduire le code répétitif des appels.
  • TypeScript pour sécuriser le modèle des cultures, attaques et insectes.

Ce que ce projet m'a appris

ArSaTool m'a appris à structurer une application autour de ses données : un catalogue, des relations (culture, attaque, insecte, images) et un circuit de validation. C'est exactement ce que je retrouve aujourd'hui dans la CMDB : des objets, leurs relations, et des règles pour garantir la qualité de l'information.
